# Architecture guide

This document describes Nodo's code structure and runtime behavior for contributors modifying the source. For a user-facing explanation, see [How it works in the README](../README.en.md#how-it-works). See the [development guide](development.md) for the development workflow.

## Overview

Nodo is a dsh plugin with three parts:

- **Host** (`index.js`, `core/`, `src/host/`): runs in the dsh process, manages projects, roles, teams, conversations, approvals, user decisions, and lead delegation, and starts Agents.
- **Client** (`client.js`, generated from `src/client/`): runs in the dsh web interface and mounts the sidebar, roles and teams pages, conversation panel, lead round view, and right sidebar into host-provided UI slots.
- **Agent adapter layer** (`agent-drivers/`, TypeScript compiled to the committed `dist/`): normalizes public Agent protocols into a common driver interface.

```mermaid
flowchart LR
    UI[dsh UI<br/>client.js] -->|DSH conversations| S[dsh session controller]
    UI -->|POST /api/nodo| C[channel.js]
    C --> H[Host modules<br/>Conversations · Teams · Leads · Approvals]
    S --> ESH[DSH native agent]
    H --> D[drivers.js]
    D --> AD[agent-drivers]
    AD --> E[Codex · Claude Code · OpenCode …]
    H --> F[(Plugin data directory)]
    H --> P[(Project directory .nodo/)]
```

## Directory structure

```text

  src/client/          Sidebar, roles and teams, conversations, settings, and the right sidebar
  agent-drivers/       Agent registration, protocol adapters, and capability interfaces

```

## Host modules

Each module under `core/src/` exports `install(rt)` and attaches its functions to the shared `rt` object. `MODULES` in `core/src/index.js` loads modules in order: `diag` comes first and provides the shared `rt.warn`; `channel` comes last and exposes interfaces over the other modules. The dsh plugin's own modules (`src/host/native-status.js`, `src/host/route.js`, `src/host/terminal.js`) install after the core modules. Modules do not call each other during installation; they interact through `rt` only at runtime.

| Responsibility | Modules |
| --- | --- |
| State and data | `store` (`state.json` and transcript reads and writes), `home-lock` (single-writer lock), `secrets` (credentials and redaction) |
| Projects and roles | `workspaces` (project directories), `worktrees` (Git worktrees), `profiles` (roles), `sessions` (conversations) |
| Agent bridging | `drivers` (driver process lifecycle), `engine-settings` (Agent settings), `dispatch` (sending, steering, and queuing messages), `approvals` (approval cards) |
| Conversation content | `prompt` (rendering role briefs, references, lead rules and delegation context sections), `session-references` (manual conversation references), `attachments` (images, attachments and staged file copies), `stream-records` (tool details), `stats` (conversation statistics), `context` (result, decision, message, tool-record and acceptance reads, plus dispatch context selection), `native-status` (plugin module in `src/host/`) |
| Teams and leads | `teams` (teams, task types, and the per-type assignment table in `prefs.teams`), `lead` (routing, dispatch, delegation context, reports, and retries), `decisions` (user decision records, the dispatch pause, answer handoff and recovery), `lead-channel` (the `nodo_lead` MCP channel exposing the board, delegation, interrupt, task, decision and context tools; served from the host's loopback MCP endpoint in `src/host/mcp.js`, with a stdio child process as fallback), `core/shared/route.js` (pure routing decision), `core/shared/lead.js` (which engines may lead) |
| Project tools | `terminal` (plugin module in `src/host/`: terminals over the host subprocess service and the `/api/nodo/terminal` route) |
| Interface | `channel` (answers `POST /api/nodo`), `route` (registers that HTTP route), `live` (pushes updates over `GET /api/nodo/live`) |

## Message paths

**Agent conversations.** Codex, Claude Code, Qoder, Pi, ZCode, OpenCode and CodeBuddy use their own drivers through `drivers.js` and `dispatch.js`. Nodo displays their messages, tool activity and approval cards in its Feed. These roles do not register dsh model providers or Agent presets.

**DSH conversations.** The dsh driver uses the host's public native session controller. Its `driverSessionId` identifies the native conversation, which opens in the host view. Native status and references use that same identifier.

**Engine context handoff.** A conversation keeps its Nodo id while the engine cursor `driverSessionId` can change; tasks, executions, reports and lead credentials are bound only to the Nodo id. When Claude Code or Codex reports that the resumed engine session no longer exists (`errorKind: 'resume-failed'`, recognised from the engine's own diagnostic naming the resumed id), `dispatch.js` clears the cursor, releases the driver, appends a note to the transcript, and resends the same message once into a new engine context that is primed with the saved task context. A second failure ends the turn normally. A lead is told to read `nodo_board` and the `<nodo-status>` snapshot to pick up active delegations.

**Lead attachments.** Files and images sent to a lead conversation are copied under the project's `.nodo/workflow-inputs/`, and their paths are appended to the message the lead receives. The executor never sees the lead's conversation, so the lead passes those paths in the task.

**Lead delegations.** `lead-channel.js` serves the lead's `nodo_board`, `nodo_delegate`, `nodo_interrupt`, `nodo_task`, `nodo_decision` and `nodo_context` tools to Claude Code and Codex over a private socket in `runtime/`, with one token per lead session. The header prepended to a delegation asks the executor to carry out the task as written, start its report with a one-line outcome summary, actual verification results and unresolved issues, and list anything left open that blocks it with possible approaches. The lead rules make the lead judge authorization itself (executors do not), write the authorized scope and the user's decisions into the delegation, and review every delivered report before delegating again. `lead.js` validates the requested task type and difficulty against the lead's team, routes it with `core/shared/route.js`, and uses `tasks.js` to persist a Task and one Execution per delegation. Each Execution binds its executor conversation, route, status, the input context it was sent with and its archived result; review of a delivered report, task completion, reopening and title/brief/relationship revisions of unfinished tasks are separate decisions through `nodo_task`. Completion takes `executionIds` of the task's own archived results, a reason and a non-empty basis; `references` is accepted only when every execution's result is missing or marked legacy, and cannot be mixed with `executionIds` or `basis`. New conversation `source` records retain their origin, while old `source.dispatch` records remain readable. Accepted executions stay queued until the lead turn ends normally, then persist running before being sent exclusively through `rt.send`. A lead session keeps up to five executions active at once and accepts at most 24 per turn; the budget resets when the user messages the lead. One turn can dispatch several independent tasks. Reports deliver first in first out, and a still-queued report never holds back a dispatch that was already accepted; a report that has just been delivered does block new delegations until the lead reviews it or attaches it to a user decision. Restart cancels queued executions as unsent and marks running executions unconfirmed. When the executor ends, `lead.js` queues one report through the existing report queue with the execution's real status, capture completeness, a preview explicitly labeled as a preview, and the result handle; a new result report creates no session reference, while manual conversation references remain separate user-created snapshots. Records that predate archived results fall back to their saved reference snapshots or summaries and are marked legacy. A stop that the engine does not confirm within 15 seconds is settled as unconfirmed, and transient engine errors that the driver classifies as retryable are continued in the same session up to five times. A delegation with `worktree:true` runs in a task worktree created from the lead workspace's HEAD on a `nodo/task-*` branch: the Execution carries its own workspace reference, the task keeps that directory across executions, worktrees of never-dispatched executions are removed automatically, and Nodo never merges — integration is a manual merge or a separate delegation without isolation. Optional Task `parentId` and `dependsOn` ids belong to the same coordinator: dispatch requires every dependency to be `done`, and parent acceptance requires every child to be `done` as well as archived results from the parent's own executions; relation changes use `nodo_task revise`, and no status changes propagate automatically.

**Session continuation.** A follow-up dispatch carries `taskId` (same deliverable) or, on a new task, `continues: <taskId>` (the next step of a long effort or work building on another task's result); the legacy `session` parameter is gone. Nodo itself decides whether the source task's last ended execution's session is reused — the receipt reports `continued` plus a reason when it is not — under fixed conditions: the session is the lead's own, unarchived, idle, its latest dispatch is not unconfirmed, the routed role and difficulty match, the execution directory matches the session workspace, an `independent` type never reuses a session that ran non-independent work, and a session retires after five executions. When the session is not reused, a fresh one opens and the source task's latest execution result is inlined into `context.required` automatically. When it is reused, the input prepends an increment note listing the later executions in the same directory that touched files this session had changed. Each execution also records a `files` summary — path, operation and capture completeness merged from the driver's confirmed change snapshots inside the execution window — shown in the report's first line as a changed-file count and appended to the full result under `nodo_context read`; the report prompt no longer asks executors to list changed files.

**Delegation context.** `nodo_delegate` composes the executor's input from the delegation header, the task text, required excerpts and a background catalog. Without a `context` argument it collects the answered decisions linked to the task's parent and dependencies, and each dependency's acceptance conclusion, and archives the dependency's last accepted execution result as background; the user's own message is never attached by default — the lead's task body carries the request. An explicit `context.required` and `context.background` list of `sourceId`s from `nodo_context list` replaces that default; each list holds at most 20 ids; an explicit required source that is unknown, unauthorized, cleaned or over budget refuses the delegation, while an unavailable background source stays listed as unavailable. Required excerpts are inlined with their descriptions and completeness marks (source ids stay in `Execution.inputContext`); background text is written through `attachments.js` into `.nodo/workflow-inputs/task-*/` under the executor's workspace (its own directory for a worktree) and only its path relative to the executor's working directory, not its text, is sent; the executor reads those files with its normal file tools, and no new executor MCP tool is added. Selections are captured when the delegation is accepted, so later transcript cleanup does not change a queued input. The composed body is limited to 96,000 UTF-16 units; ordinary messages and the lead's task text plus delegation header keep the existing 32,000 limit, while background text is limited to 4,000,000 UTF-16 units; selection errors, authorization, background size and an estimated required total are checked before a new task, worktree or dispatch slot is allocated, while the final body limit is checked again and background files are materialized before sending, and a stop or failure there leaves the dispatch unsent. `startExecution` records the body length, a preview, the required descriptors and the background catalog as `Execution.inputContext`.

**Execution results.** For an execution ended by the current version, `Execution.result` holds the final text, `completeness` (`complete`, `partial` or `unavailable`), a reason (`null` when complete), a whitespace-collapsed preview of at most 200 characters, the stored length and the original length. `dispatch.js` carries the engine's full final message into the archive, while the transcript's display copy is clipped to 16,000 characters. The first archive wins, except that an unconfirmed execution with a missing final can be filled by a late one. Results are cut to 1,000,000 UTF-16 units each and to 16,000,000 in total; a cut result is `partial`, one that cannot store text is `unavailable`, and both carry reason `storage-limit`. A capture from a turn that did not end normally, or from an unconfirmed execution, is `partial` (`capture-incomplete`); a missing final is `unavailable` (`missing-final`); a current-version execution that has not ended reads as `unavailable` (`not-archived`). `nodo_board` returns only previews and handles for results, while `nodo_context` reads the stored text: `list` filters by `taskId` and `query` and returns at most 50 descriptors with `nextCursor`; `read` pages by `offset` and `limit`, default 8,000 and at most 16,000 UTF-16 units, and accepts an execution's id directly as `executionId` in place of the `execution:<id>:result` handle. Handles are `execution:<id>:result`, `decision:<id>`, `message:<sessionId>:<timestamp>:<hash>`, `tool:<conversationId>:<ref>` and `task:<taskId>:acceptance`; they resolve to the existing execution, decision, transcript, tool-detail and task records, with no separate source store. Messages and tool records are limited to the lead session and the executor sessions it dispatched; decisions to the lead's own session; executions and acceptances to its own tasks. A cleaned message or tool record reads as `unavailable`; results saved before archiving existed read from their old reference snapshot or summary as `partial` (`legacy-reference` or `legacy-report`) or as `unavailable` (`legacy-unavailable`). Reading never marks a review or accepts a task; the lead rules require it to check the recorded status and completeness, not just the preview, before review or acceptance.

**User decisions.** `decisions.js` keeps a lead's request in `state.decisions`: one unfinished request per lead session, carrying its questions, options, recommendation, linked tasks, source executions, references and `stopExecutionIds`. Creating one marks the source reports `ask` and pauses the session with `orch/decision-pending`: new delegations, automatic retries, report wake-up, acceptance of the related tasks and their ancestors (every task in the session when nothing is linked), and archival are all refused; delegations not yet sent are cancelled and only the listed executions are interrupted. The user answers or cancels through `channel.js` (`decision-answer`, `decision-cancel`) from the card in the team conversation, whose unsent answers live in `localStorage`. An answer stays `answered` and blocking until the queued input actually starts a new lead turn, when the decision becomes `delivered` and a `decision-delivery` transcript row records the handoff; an answered decision left by a restart is re-queued, a cancelled one appends a note and releases the pause, and a lead can neither answer nor cancel. Unlike an approval card, which mirrors a live engine request, a decision outlives the turn that raised it. Reports delivered before this record existed are not marked for review afterwards.

## Client

`scripts/build-client.mjs` bundles `src/client/` (ESM, plus `core/shared/` data) into `client.js` with esbuild and inlines assets such as icons. dsh loads `client.js` as a plain script. React and UI components are supplied by the host and are not bundled separately.

The client mounts its parts through host UI slots, including run status and references above the composer, conversation message nodes, and tool detail views. UI state such as drafts and navigation is saved in the browser's `localStorage`.

All mounted surfaces share one live data source and one GET NDJSON stream at `/api/nodo/live`. After the initial state and transcript reads, the host combines changes over 100ms and pushes running status, approvals, statistics, session activity and subscribed transcript deltas. Each transcript subscription carries its last position for reconnects; unchanged rows retain their object identity in the client. Structural changes trigger a full state read. Runtime session metadata is persisted without changing the structure version and arrives through the stream. While disconnected, the shared source falls back to incremental polling and retries the stream with exponential backoff from one to 30 seconds. Unmounting the last subscriber aborts the connection and clears its timers; the host releases subscriptions on cancellation or plugin unload.

The sidebar rail switches between the projects tree and the roles page. The tree lists projects only: sessions that run in worktrees group under their owning project, and a single worktree is removed from its parent project's menu. The roles page carries the team editor: a grid of role cards, one column per team with a lead slot and a member column, and a per-team task assignment table. Dragging a card into a lead slot makes it that team's lead; a lead leads one team and belongs to no member list.

In the team view a lead conversation on a non-dsh engine takes one sidebar row: the executor conversations it dispatched are grouped under that row instead of listing separately, and the row's status, time, highlight, role filter and search cover the group. Its page renders the transcript as a round view — the lead's own messages, each dispatch as a chip, and the executor's result preview beneath it — with 查看会话 switching to the executor conversation, 停止 ending a live delegation, and statuses such as 结果未确认, 已取消, 已中断, 未回报, 等待自动继续, and 等待用户. An unfinished decision renders as a card below the round view with the question, each option's cost, the recommendation and its reason, the linked tasks, the executions still running or stopping, and a two-step cancel; the feed renders a submitted answer as its question and chosen option instead of the stored JSON. The merge is driven by record fields rather than text: dispatch notes carry `delegation`, executor conversations carry `source.leadSessionId`, and sessions without them render as ordinary conversations. Executor conversations on the dsh engine are not grouped, and the same conversations list separately in the 角色 view. Long silence only marks a turn as suspected stuck, without failing it; an unconfirmed stop frees that delegation's slot after 15 seconds.

Nodo conversation pages, their legacy shells before a session exists, and `NewConversation` draft welcomes with a selected project own a right sidebar in the host's `rightbar` slot, with tabs for project files, turn changes, terminals, and a browser. Legacy shells keep their existing content and drafts; `NewConversation` binds the Nodo sidebar only for drafts rendered by `NodoEntry`. Read-only conversation pages retain files, changes and the browser but do not restore or operate terminals. File-changes cards open a single replaceable changes tab with a snapshot and an independent `stream-detail` reader, so saved details remain loadable after the card unmounts. The read-only `workspace-dir` and `workspace-file` endpoints accept a workspace or a session target and render files with host primitives. The read-only `task-list` and `task-get` endpoints read the lead task board, scoped by workspace or team where given. Terminal operations accept `{ workspace }` or explicit `{ profile, session }`; the server validates the target and groups terminals by the real working directory, including worktrees, without trusting a client-supplied cwd. A valid session without a working directory lists terminals as unavailable. Output streams as NDJSON from `/api/nodo/terminal`; the browser uses the desktop host's leased webview when available and an iframe otherwise. Open state and tabs live in memory and survive switches within the same directory: after a page refresh terminals are listed again and replayed from their buffers, while file, changes and browser tabs are not restored. Terminals end when their tab closes, when no live workspace or unarchived conversation references their directory, or when the plugin unloads. Native welcomes and Nodo sessions opened in the native conversation view keep dsh's own right sidebar.

## Agent adapter layer

`agent-drivers/` is a separate package embedded in the plugin and can be patched and versioned independently. Each driver implements the same eight primitives: `openSession`, `sendTurn`, `steer`, `interruptTurn`, `respondToRequest`, `onEvent`, `hasSession`, and `dispose`. Agents are registered in `ENGINES` in `agent-drivers/src/index.ts`; the registration metadata also serves client builds and verification scripts.

See the [Agent adapter overview](../orchestrator/agent-drivers/README.md), [driver interface and event protocol](../orchestrator/agent-drivers/PROTOCOL.md), and [Agent intake workflow](../orchestrator/agent-drivers/ENGINE_INTAKE.md).

## Data storage

The plugin data directory defaults to `~/.dsh/orchestrator/`, or the `orchestrator/` subdirectory of `DSH_HOME` when set. It can also be specified through the plugin's `config.home`.

| Location | Contents |
| --- | --- |
| `state.json` | Projects, roles, conversations, `tasks` with their acceptances, `executions` with their input context and archived results, `decisions`, engine catalogs, and preferences including teams and their task assignments |
| `activity.json` | Transcript lengths and last activity, conversation statistics, and the tool detail ownership index |
| `transcripts/` | One append-only `.jsonl` transcript per conversation; incomplete trailing rows are ignored on read |
| `state.lock` | Write lock: only one dsh can write to the same data directory; other instances are read-only |
| `secrets.json` | Credentials, with mode 600; drivers receive them through `ORCH_SECRET_*` environment variables |
| `attachments/`, `files/` | Pasted images and attachments |
| `references/` | Manual conversation reference snapshots; report snapshots written by older versions remain readable as legacy results |
| `stream-details/` | Tool call details |
| `identities/`, `drivers/`, `agents/` | Role identity files and working directories used by drivers |
| `runtime/` | Private lead channel socket and its per-session tokens; removed when the plugin unloads |
| `workspaces/` | Working directories created for legacy roles that had none |

State and activity files are written through a temporary file followed by a rename. During a turn, saves are combined at one-second intervals; turn completion and plugin shutdown flush pending writes. Rows of a running turn are written to a per-conversation `.open` journal with each combined save, and append to the JSONL when the turn settles; on load, a journal left by an interrupted host is appended first. History is read on demand, with at most 16 rows and 64KB cached per conversation. Files exceeding 800 rows are compacted on load, or after a write once they reach twice that. An older `.json` transcript migrates on first read and is renamed to `.json.bak`. An unreadable transcript is left unchanged and logged; when its conversation gets new rows, an unreadable `.jsonl` is renamed to `.jsonl.broken-<time>` and a new file starts. `state.json` carries version 5; upgrading a file saved by an older version keeps the original as `state.v<version>.json`, and an older Nodo treats version 5 as newer, neither loads nor overwrites it, and reports that the plugin must be updated. Older embedded transcripts are moved out of `state.json` as they are read. Removing retired state fields or moving the tool detail index keeps `state.retired.json.bak`. The project's `.nodo/` stores Git worktrees, manual and per-task, under `worktrees/`, plus copies of files and images sent to a lead and delegation background material under `workflow-inputs/`, and Nodo automatically writes a `.gitignore` there.

Deleting a role marks it with `deletedAt` and archives its conversations; deleting a project archives the conversations that ran in it and records the original project name in `workspaceName`, and the project's worktree records are removed with it while their directories and branches stay on disk. Every archived conversation keeps its `cwd`, `workspaceRef`, and the role and project names it had. Transcripts, statistics, references, tool details, and identity files remain available. A deleted role leaves every team it was in, a team it led loses its lead, and task routing no longer offers it; it no longer holds a name or a slot under the profile limit, so its name can be reused.

Archived conversations open read-only from the global 已移除 entry; the client requests no task and does not open or select the session on the engine, and the host refuses send, compact, select, update, and unarchive requests for them. Manually archived conversations in existing projects stay in that project's archive filter and also open read-only; unarchiving restores writing while the project still exists. Conversations saved before archival was recorded, with no `archivedAt` and no project, remain writable and are not migrated.

Before a role or project is deleted, the DSH twins of its conversations are archived through the host workspace registry; a failure rolls back the archives that call made and leaves Nodo's records unchanged. Hosts without that interface skip synchronization, and other engines' threads are retained without synchronization. A DSH conversation with no local transcript is read back through the host session inspect call.
